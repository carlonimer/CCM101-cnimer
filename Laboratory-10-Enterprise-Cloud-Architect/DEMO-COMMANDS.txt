# PALIWANAG: Bubuksan nito ang CloudNova Enterprise Web Portal. Ipakita ang UI, pindutin ang 'Test PostgreSQL Ping' (sub-15ms latency).

# A4. Web Application Health Telemetry Probe (Curl)
# PALIWANAG: HTTP GET request sa /health endpoint. Kapag nag-return ng 200 OK at {"database":"connected","status":"healthy"}, buo ang 3-tier communication!

# A5. Perimeter Firewall Test: Bukas ang Allowed Ingress Ports (Web at SSH)
# PALIWANAG: Dapat mag-return ng 'TcpTestSucceeded: True' para sa port 8088 (Web) at port 22 (SSH) dahil pinapayagan ito ng UFW.

# A6. Perimeter Firewall Test: Naka-BLOCK ang Database at App Ports (Security Isolation Proof!)
# PALIWANAG: Dapat mag-return ng 'TcpTestSucceeded: False' o mag-timeout para sa port 5432 (PostgreSQL) at 5000 (Flask).
# SASABIHIN: 'Patunay ito na kahit may database sa loob ng VM, protektado ito ng Default Deny policy ng firewall at network isolation, kaya walang external attacker na makakapasok nang direkta.'

 BAHAGI D: LIVE DATA PERSISTENCE PROOF (SURVIVES CONTAINER DOWN & REBOOT)
 Layunin: Patunayan na hindi nawawala ang database records kahit sirain ang mga containers.
------------------------------------------------------------------------------

# D1. Gumawa ng test table at mag-insert ng bagong record na may live timestamp
# PALIWANAG: Magpapasok tayo ng bagong test record sa loob ng PostgreSQL container.
docker compose exec -T db sh -c 'psql -U $POSTGRES_USER -d $POSTGRES_DB -c "CREATE TABLE IF NOT EXISTS demo(id serial PRIMARY KEY, note text, created_at timestamp default now());"'
docker compose exec -T db sh -c 'psql -U $POSTGRES_USER -d $POSTGRES_DB -c "INSERT INTO demo(note) VALUES (\x27Mission 10 Persistence Proof\x27);"'
docker compose exec -T db sh -c 'psql -U $POSTGRES_USER -d $POSTGRES_DB -c "SELECT * FROM demo;"'

# D2. I-destroy ang lahat ng containers gamit ang docker compose down
# PALIWANAG: Binabagsak at tinatanggal natin ang lahat ng containers upang gayahin ang pagkasira ng system.
docker compose down
docker compose ps

# D3. Muling buhayin ang stack gamit ang docker compose up -d
# PALIWANAG: Muling itatayo ang mga fresh containers mula sa images.
docker compose up -d
sleep 3

# D4. I-query ang demo table muli: NANDITO PA RIN ANG DATA!
# SASABIHIN: 'Kahit tinanggal at muling itinayo ang mga containers, buo pa rin ang record natin sa demo table dahil sa ating persistent named volume!'
docker compose exec -T db sh -c 'psql -U $POSTGRES_USER -d $POSTGRES_DB -c "SELECT * FROM demo;"'


------------------------------------------------------------------------------
 BAHAGI E: AUTONOMOUS BACKUP AT DISASTER RECOVERY SIMULATION
 Layunin: Patunayan ang automated backups, cron scheduling, at sub-60s recovery.
------------------------------------------------------------------------------

# E1. Patakbuhin nang manu-mano ang automated backup script
# PALIWANAG: Kumukuha ito ng compressed database snapshot (.sql.gz), nagse-set ng secure 0600 permissions, at naglilinis ng lumang backups (>7 days).
./scripts/backup-db.sh

# E2. I-audit ang Backup Files, File Permissions at Cron Job Schedule
# PALIWANAG: Ipinapakita ang nabuong archive na may 0600 permissions at ang automated cron job na tumatakbo araw-araw ng 2:00 AM.
ls -lah backups/
echo "--- CRON JOB SCHEDULE ---"
crontab -l | tail -n 2

# E3. Suriin ang Archive File Integrity (Gzip CRC-32 Test)
# PALIWANAG: Non-destructive test gamit ang gzip -t upang patunayan na walang corruption o bit rot sa backup archive.
LATEST=$(ls -t backups/cloudapp_*.sql.gz | head -1); echo "Pinakabagong backup: $LATEST"
gzip -t "$LATEST" && echo "Backup integrity verified: 100% OK!"

# E4. Disaster Simulation: Aksidenteng Pagbura ng Data (Drop Table)
# PALIWANAG: Buburahin natin ang demo table gamit ang DROP TABLE para gayahin ang data loss.
docker compose exec -T db sh -c 'psql -U $POSTGRES_USER -d $POSTGRES_DB -c "DROP TABLE demo;"'
# I-verify na nawala ang table (magre-return ng error: relation "demo" does not exist):
docker compose exec -T db sh -c 'psql -U $POSTGRES_USER -d $POSTGRES_DB -c "SELECT * FROM demo;"'

# E5. Disaster Recovery: I-restore ang Database Snapshot mula sa Gzip Pipeline
# PALIWANAG: Sa isang linya ng pipe, idine-decompress ang backup at ipinapasok pabalik sa PostgreSQL engine.
gunzip -c "$LATEST" | docker compose exec -T db sh -c 'psql -U $POSTGRES_USER -d $POSTGRES_DB'

# E6. Patunayan na NAKABALIK ANG DATA!
# SASABIHIN: 'Sa loob lamang ng ilang segundo, naibalik natin ang nawalang database table mula sa ating compressed backup. 100% successful ang ating Disaster Recovery na may RTO na mas mababa sa 15 segundo!'
docker compose exec -T db sh -c 'psql -U $POSTGRES_USER -d $POSTGRES_DB -c "SELECT * FROM demo;"'
